# 分支开发与提交

把用户指定的变更做成可审查、可回退的本地 Git 提交。保留用户原有改动，不把无关文件混入提交。

## 工作流程

1. 读取适用的项目规范，检查 `git status --short`、当前分支、近期提交和已有差异。记录原有脏文件；不要用 reset、clean、checkout 文件等操作清掉用户工作。
2. 用户指定分支时遵从；否则从当前确认的基线创建 `codex/<简短任务名>`。已在本任务分支则继续使用。已有改动是否属于任务，按内容判断；不能仅因文件未跟踪就丢弃或全盘提交。默认不在 main/master 直接开发。
3. 实现用户授权范围，针对数据完整性、交互或规则变化补有意义的回归测试。文档和调研与代码分别整理；检查失败先修复或明确记录无法验证的原因，不声称未做的验证通过。
4. 提交前检查完整差异和 `git diff --check`，执行项目要求的检查。这个仓库的运行检查是 `npm run test` 和 `npm run build`；页面变化还需浏览器核对。避免把 node_modules、dist、临时截图、备份或敏感配置纳入提交。
5. 按路径或补丁显式暂存本次变更，并检查 `git diff --cached --stat` 和暂存内容。不要默认 `git add .`。把独立目的分成独立提交，例如修复、可复用技能、玩法研究。
6. 用户已明确要求提交时，验证后直接本地 commit；不再重复索要确认。标题说明具体问题或行为，正文只保留关键原因、兼容处理和验证结果，遵从仓库已有提交风格。多行正文用文件传给 Git，确保真实换行。
7. 复查分支、提交哈希和工作区状态，报告提交内容与验证结论。剩余用户改动应保留并说明。推送、PR、合并和部署按当前请求的授权范围处理，创建分支与本地提交本身不扩大这些权限。

如果 .git 写入被沙箱限制，针对已获授权的具体 Git 操作请求工具提权；不要绕过限制或通过修改权限解决。失败时保留工作树与测试结果，准确说明阻碍。
